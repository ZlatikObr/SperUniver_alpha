# AI Policy — SperUniver_alpha / WriteOff Doctor

> Этот документ — обязательный раздел Артефакта 1 PDLC. Описывает границы, источники, формат вывода и поведение AI-агента в неоднозначных ситуациях.

## 1. Scope (область применимости)

AI-агент работает **только** с задачей анализа списаний продуктового ритейла и рекомендациями по AI-внедрениям для сокращения этих списаний.

**В scope:**
- Структурный анализ списаний по категориям, точкам, периодам.
- Сопоставление профиля клиента с базой публичных кейсов AI-внедрений.
- Расчёт ожидаемого ROI трёх инициатив на данных клиента и бенчмарках рынка.
- Генерация структурированного PDF-отчёта.

**Вне scope (агент отказывает):**
- Юридические и налоговые консультации.
- Прогноз курсов / котировок / финансовых рынков.
- Любые рекомендации, касающиеся конкретных людей (сотрудников, конкурентов).
- Анализ непродуктовых вертикалей (одежда, электроника и т.д.) — на MVP.
- Прогноз спроса / ценообразование в реальном времени.

## 2. Источники данных

| Источник | Использование | Ограничения |
|---|---|---|
| **CSV/Excel клиента** | Первичный источник для анализа | Должен соответствовать схеме `WriteoffRow`. Минимум 30 дней. |
| **`data/cases_db.json`** | База из 10 публичных кейсов для бенчмаркинга | Только из открытых источников (пресс-релизы, TAdviser, Habr). Каждый кейс имеет URL-ссылку на первоисточник. |
| **`configs/benchmarks.yaml`** | Усреднённые показатели рынка | Декларируется как «диапазон, основанный на публичных данных». |

**Запрещено:**
- Внешние API на инференсе (Google, web search, vendor APIs).
- Любые персональные данные сотрудников / клиентов.
- Данные конкурентов клиента, не помеченные публичными.

## 3. Формат вывода

Каждый шаг пайплайна возвращает строго типизированный объект (Pydantic-модель из `src/schemas.py`):

| Шаг | Контракт | Обязательные поля |
|---|---|---|
| Validator | `ValidatedDataset` | `profile`, `rows`, `period_months`, `quality_score` |
| Analyzer | `AnalysisResult` | `top_categories`, `top_stores`, `seasonality`, `anomalies`, `overall_loss_pct_revenue` |
| CaseMatcher | `list[MatchedCase]` | `case_id`, `relevance_score`, `why_relevant` |
| InitiativeGenerator | `list[Initiative]` (3 шт) | `title`, `investment_rub`, `payback_months`, `expected_loss_reduction_pct`, `confidence` |
| ROICalculator | `ROIReport` | `annual_savings_total_rub`, `total_investment_rub`, `blended_roi_x`, `assumptions` |
| Reporter | `MarkdownReport` | `content`, `metadata` |

**Финальный PDF-отчёт** обязательно содержит разделы:
1. Профиль клиента
2. Структура потерь (текущее состояние)
3. Топ-3 инициативы с числами
4. Ожидаемый совокупный эффект
5. Ограничения и допущения расчёта
6. Дисклеймер

## 4. Поведение при недостатке данных

Агент **никогда не выдумывает числа**. При недостатке информации он:

1. Возвращает явный статус:
   ```json
   {
     "status": "insufficient_data",
     "missing": ["период_менее_30_дней", "одна_категория"],
     "recommendation": "Загрузите данные за минимум 90 дней по всем категориям"
   }
   ```
2. Прерывает дальнейшие шаги пайплайна.
3. UI показывает понятное сообщение с инструкцией клиенту.

**Триггеры для отказа:**
- Период данных < 30 дней.
- Менее 100 строк после очистки.
- Отсутствует более 50% значений в обязательных колонках (`category`, `total_loss`).
- `quality_score < 0.4` после валидации.

## 5. Поведение при низкой уверенности

Если `confidence < 0.5` для конкретной инициативы:
- Инициатива помечается флагом `requires_expert_validation: true`.
- Числа приводятся как **диапазон**, не как точка (например, «5–9 млн ₽ экономии» вместо «7 млн ₽»).
- В PDF-отчёте выделяется визуально с примечанием: «Требуется верификация очным аудитом».

## 6. Запрещённые выводы

Агент **не имеет права** возвращать:
- Утверждения о краже / мошенничестве сотрудников.
- Выводы о конкретных физических лицах.
- Юридические или налоговые рекомендации.
- Точные обещания ROI без диапазона и допущений.
- Сравнения с конкретными конкурентами клиента.
- Маркетинговые рекомендации (вне scope).
- Прогнозы цен на сырьё, валютные курсы.

Это enforced на уровне system prompt (`prompts/*.yaml`) и валидируется на постпроцессе (Pydantic-модели имеют ограничения).

## 7. Эскалация

Агент рекомендует эскалацию (очный аудит / эксперт) если:
- Период данных от 30 до 90 дней (мало для сильных трендов).
- `quality_score` от 0.4 до 0.6.
- Любая из топ-3 инициатив имеет `confidence < 0.5`.
- В данных обнаружен резкий разрыв (более 60 дней без записей).

Эскалация показывается в отчёте как отдельный раздел: **«Что мы рекомендуем проверить очно»**.

## 8. Логирование и наблюдаемость

Каждый запуск пишет JSONL-лог в `logs/{run_id}.jsonl` со следующими полями для каждого шага:

```json
{
  "run_id": "uuid",
  "step": "case_matcher",
  "model": "claude-sonnet-4-6",
  "input_tokens": 8123,
  "output_tokens": 1872,
  "latency_ms": 4321,
  "cost_usd": 0.054,
  "confidence": 0.78,
  "status": "ok",
  "timestamp": "2026-05-04T10:38:48Z"
}
```

Эти логи — единственный источник правды для расчётов в Артефакте 3 (экономика).

## 9. Версионирование промптов

Все промпты — в `prompts/*.yaml` с явным версионированием. При изменении промпта на demo-репе — обязательно поднять версию в комментарии файла, иначе тесты не воспроизводятся.

## 10. Ограничения политики (честно для жюри)

- AI Policy спроектирована для MVP-демо. Production-версия потребует:
  - Юридического ревью на ответственность за рекомендации.
  - Опционального human-in-the-loop для финальной выдачи.
  - Audit trail для регулятора (152-ФЗ при обработке выгрузок).
  - SLA на корректность отказов (false-positive insufficient_data).
- На MVP не реализовано: анти-prompt-injection защита, rate-limiting на пользователя, мониторинг hallucinations в production.
