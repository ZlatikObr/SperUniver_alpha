# Критерии оценки МФТИ — стратегия максимизации баллов

## Общая цель: 38–40 / 40 (сильный PDLC-MVP)

4 критерия, каждый по 10 баллов. Минимум для прохождения: 4 балла по каждому + 24 суммарно.

---

## Критерий 1. Артефакт 1 — PDLC-спецификация (цель: 10/10)

| Признак | Баллы | Наш план |
|---|---|---|
| Проблема сформулирована | +1 | См. `00-brief.md` и `01-target-audience.md` |
| ≥2 User Story с AC | +2 | Пишем 3 (диагностика, отчёт, отказ при нехватке данных) |
| DoD для AI-функции | +2 | Чёткие критерии: формат вывода, обязательные поля, валидация чисел |
| AI Policy | +2 | Явные границы: только загруженные данные + БД кейсов; отказ при недостатке; никаких выводов о людях |
| Ограничения и риски MVP | +1 | См. `03-mvp-scope.md` раздел «Что НЕ входит» |
| Спец согласована с архитектурой | +2 | Связка через диаграмму потока данных в Артефакте 1 |

**Чего избегаем:**
- ❌ User Stories как технические требования (всегда формат «Как [роль], я хочу [действие], чтобы [ценность]»)
- ❌ Формальная AI Policy (наша — конкретная, с примерами отказов)
- ❌ Описание идеального будущего продукта (явно отделяем MVP от roadmap)

---

## Критерий 2. Артефакт 2 — Прототип (цель: 10/10)

| Признак | Баллы | Наш план |
|---|---|---|
| Запускается без ручной магии | +2 | `make demo` или `streamlit run app.py` — одна команда |
| Основной сценарий E2E работает | +3 | Главный приоритет — это даёт треть всех баллов критерия |
| AI-компонент работает (RAG/агент/prompt) | +2 | Используем все три: RAG по кейсам + цепочка промптов + агент-оркестратор |
| Логирование шагов | +1 | JSONL-лог каждого шага агента |
| Промпты и конфиги версионированы | +1 | YAML-файлы в репо, не хардкод |
| ≥5 тест-сценариев | +1 | См. `03-mvp-scope.md` |

**Критические минусы (избегаем!):**
- ❌ Прототип не запускается → −4 (это дисквалификация)
- ❌ Команда не понимает, как работает AI → −3 (тренируем Q&A)
- ❌ Нет README → −2

---

## Критерий 3. Артефакт 3 — Экономика и метрики (цель: 10/10)

| Признак | Баллы | Наш план |
|---|---|---|
| Cost-per-task | +2 | Считаем токены × тариф Sonnet 4.6 + латентность + инфра |
| 2 сценария (base/optimistic) | +2 | Base: 20 аудитов/мес. Optimistic: 80 аудитов/мес |
| Trade-offs (качество/скорость/цена) | +2 | Sonnet vs Haiku: качество vs цена; разбираем выбор |
| ROI с привязкой к продуктовым метрикам | +2 | LTV / CAC, конверсия freemium → paid, retention |
| Ограничения и допущения | +2 | Явный раздел «о чём расчёт молчит» |

**Чего избегаем:**
- ❌ ROI декларативный — у нас только числа
- ❌ Сценарии-близнецы — base и optimistic различаются на 4× по объёму

---

## Критерий 4. PDLC-целостность и питч (цель: 10/10)

| Признак | Баллы | Наш план |
|---|---|---|
| Питч по PDLC-логике | +2 | Структура: проблема → требования → архитектура → реализация → тесты → экономика |
| Все три артефакта связаны | +3 | Сквозной нарратив через один пользовательский кейс |
| Питч соответствует демо | +2 | Репетируем с реальным запуском, не «как должно быть» |
| Реалистичные следующие шаги | +1 | Не «выходим на IPO», а «интеграция с 1С API → пилот с одной сетью» |
| Вклад каждого участника понятен | +2 | См. README — у каждого зона ответственности; в Q&A каждый объясняет свой блок |

**Критические минусы:**
- ❌ Заявления противоречат демо → −3 (репетиция обязательна)
- ❌ Артефакты как независимые блоки → −3
- ❌ Рассказ о будущем продукте → −2

---

## Контрольный чек-лист перед питчем

- [ ] Прототип запускается одной командой
- [ ] E2E сценарий проходит на демо
- [ ] У каждого артефакта есть ссылка на остальные два (сквозная связь)
- [ ] Числа в питче = числа в Артефакте 3
- [ ] Каждый член команды может объяснить свой блок и блок соседа
- [ ] Раздел «ограничения» присутствует в каждом артефакте
- [ ] Хотя бы одна репетиция с таймером
